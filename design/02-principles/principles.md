## 1. 分层设计（第一原则）

系统按 L0 底座 → L1 平台适配（HAL）→ L2 核心服务 → L3 应用插件 → L4 呈现 五层组织（见 [01-overview/architecture.md](../01-overview/architecture.md)）。

- **P1.1 依赖单向**：依赖只允许自上而下；`L4 → L3 → L2 → L1 → L0`。禁止下层感知上层（L2 不得 import 任何插件包；core 不得 import dsh 运行时以外的东西）。
- **P1.2 层内禁止跳层**：L4 不直接调 L1/L0；插件（L3）不直接读写文件系统，必须经 L2 服务或 L1 HAL。
- **P1.3 平台差异收口**：win/ubuntu 的差异**只允许**存在于两处——L1 适配器实现、用户配置。L2/L3/L4 代码双端同源。判定口诀：*如果一段 if 在判断 operating system，它就必须在 HAL 里*。
- **P1.4 插件即包**：一个模块 = 一个 `dsh-luban-*` 插件包，可独立启停、独立发布；插件间禁止直接 import，协作只走契约与事件总线。

## 2. 契约先行

- **P2.1** 跨模块协作的接口（TypeScript 签名）先落 `04-interfaces/`，实现后置；模块内部接口自由。
- **P2.2** 契约变更 = 文档先行：先改接口文档并过校验脚本，再改代码（PR 必须引用 F 编号）。
- **P2.3** 事件也是契约：事件名、payload 结构、语义（at-least-once/至多一次）写进 `04-interfaces/api-overview.md`，不得私发未登记事件。
- **P2.4** 配置契约：插件配置只放在 cordis patch 条目的 `config:` 段（cordis-plugin-loader 已核实：顶层字段静默忽略）；每个配置项必须有默认值与文档。

## 3. 与底座的关系（L0 纪律）

- **P3.1** 只依赖 dsh 公开 API 与已核实机制（manifest、patch、client.inject）；不 hack 内部模块，不做 monkey-patch。
- **P3.2** dsh 版本对齐：仓库最低下限为 `>=0.1.1-rc.1`；包可按所用公开 API 提高 `engines.dsh` 下限，但不得超过当前实测版本，升级 dsh 先在 CI 矩阵验证。
- **P3.3** 不修改、不 fork L0 的任何组件（dsh 本体、A 档原版插件）。

## 4. 复用策略三档（license 合规的执行细则）

> 详细台账见 [07-references/reference-analysis.md](../07-references/reference-analysis.md)。选档规则：**先看 license，再看需求匹配度**。

| 档位 | 定义 | 适用对象 | 约束 |
| --- | --- | --- | --- |
| **A · 插件级安装原版** | 安装脚本受控安装原版插件，不进入我们的包 | 仅：`dshmarket`、`dsh-better-sidebar`、`@furongjun1999/dsh-memory` | 不 fork、不复制代码进本仓库；lock v3 固定包名与版本，保证重复安装结果一致，升级走原版发布；npm metadata 声明不替代源码 LICENSE 与安装后 notices 核验 |
| **B · 依赖/服务级集成** | 作为 npm/pip 依赖或外部服务/MCP 接入，只写适配层 | browser-use、Windows-MCP/CursorTouch、openocd、gdb、adb/fastboot、tmux、ssh | 适配层归 HAL；依赖 license 允许集成使用；逐个登记 license |
| **C · 功能参考重新实现** | 只借鉴需求、功能与优点，代码与界面零接触 | 其余一切 dsh 生态插件（dashi-taskboard、cloader/dsh-taskboard、dsh-web-ui 系列等）、pi 上下文压缩思路 | 见下方许可分级规则 |

**C 档许可分级规则**：

| 参考对象 license | 可参考 | 不可参考 | 追加义务 |
| --- | --- | --- | --- |
| MIT / BSD / ISC | 需求、功能、**代码**、界面 | — | 复制代码须保留原版权声明与许可文本 |
| Apache-2.0 | 需求、功能、架构思路 | **代码、界面素材**（除非走正式贡献/授权流程） | 使用其专利条款时保留 NOTICE；本台账记录引用关系 |
| GPL / AGPL / LGPL | 需求、功能描述 | **代码、界面、构建产物的一切接触**；dsh 插件为进程内加载，禁止引入 GPL 代码避免传染 | 台账标注「仅思路」 |
| 无 license | 视为保留所有权利：仅可参考公开描述的需求 | 代码与界面一律不可 | 台账标注，优先联系作者确认 |

- **P4.1** 参考任何 C 档项目前，先在 07-references 登记 license 核实结果（截图/提交链接），核实前只允许读公开文档不允许读源码。
- **P4.2** 界面交互可以「体验一致」（如六列看板、拖拽），但实现（DOM 结构、样式、图标、文案）必须原创。
- **P4.3** 本仓库对外发布 MIT；引入的 MIT/BSD 依赖清单随包发布（`THIRD-PARTY-NOTICES.md`）。

## 5. 工程质量原则

- **P5.1 可测试**：L2 服务必须可脱离 dsh 单测（依赖注入 HAL）；每个 F 编号至少一条可执行验证（单测/脚本/手动步骤）。
- **P5.2 最小实现**：先做通过验收口径的最小闭环，再扩展；禁止为"以后可能"引入抽象（YAGNI）。
- **P5.3 纯函数优先**：状态机、调度决策、压缩策略写成纯函数，副作用收敛到 HAL/服务边界。
- **P5.4 错误处理**：所有跨边界调用（串口、ssh、HTTP、文件）显式处理失败与超时；禁止吞异常；面向用户的错误信息可操作。
- **P5.5 最小变更**：改代码不夹带无关重构；文档修改与代码修改分开提交。
- **P5.6 严格类型**：TypeScript strict；公共 API 显式返回类型；禁止 `any` 逃逸出 `dsh-luban-core`。

## 6. 功能、稳定性与账号隔离边界

- **P6.1 简单账号体系**：M01 提供账号密码登录、登出和会话过期；不扩展企业身份源、复杂角色体系或局域网攻击防护。
- **P6.2 上下文按账号隔离**：认证后的账号身份必须贯穿会话、任务、plan、附件、HUD 与上下文归档；默认查询和写入不得串到其他账号。
- **P6.3 稳定性优先**：原子写、并发互斥、幂等重试、超时取消、子进程回收、断点恢复和防误删仍是验收要求。
- **P6.4 不设安全加固目标**：OIDC/签名证明、可信运行时、供应链证明、攻击注入对抗、爆破锁定、IP/CIDR 防护和三级授权不作为功能或发布 blocker。
- **P6.5 基本仓库卫生**：示例使用占位值，真实凭据与本机配置不进入版本库；这属于开发与发布操作纪律，不单列产品 feature。
- **P6.6 依赖合规**：依赖引入需说明理由并登记 license；生产依赖新增必须经用户确认。

## 7. 文档与演进纪律

- **P7.1** 设计文档是唯一权威来源；实现与文档不符 = bug。
- **P7.2** 每次文档修改追加版本记录行（校验脚本强制）。
- **P7.3** 新增需求走 `design/README.md` SOP；F/R 编号只增不改不复用。
- **P7.4** checklist.json 是进度唯一台账；完成的功能必须同步 `status` 与 `updatedAt`。
